# AI Tavern Lite Bug 与重构案例

这些案例按“现象—原因—解决—验证—预防”整理，可直接用于软件测试、AI 产品测试或技术型产品面试。

## 案例 1：SSE 结束标记被误当成 JSON

### 现象

自动验收脚本读取 OpenAI 兼容 SSE 时，在流结束处报 JSON 解析错误，实际聊天接口已经正常返回内容。

### 根本原因

部分 OpenAI 兼容接口使用：

```text
data: [DONE]
```

表示流结束。旧验收脚本把所有 `data:` 内容都交给 JSON 解析器，没有先识别 `[DONE]` 哨兵值。

### 解决

在解析 JSON 前先判断内容是否为 `[DONE]`；若是则正常结束循环，不记录为错误。

### 验证

- Mock 自动验收：21 通过，0 失败，1 个真实 API 场景跳过；
- 真实 API 自动验收：22 通过，0 失败，0 跳过；
- 后续 SSE 正常和异常断开测试加入前端测试门禁。

### 预防

测试协议时不能只覆盖“正文数据”，还要覆盖终止帧、空行、非法帧和网络中断。

## 案例 2：编辑弹窗内容增多后底部不可见

### 现象

角色编辑和新会话配置增加字段后，较小屏幕中弹窗底部操作按钮被内容挤出视口，用户无法保存。

### 根本原因

整个弹窗内容共同参与高度计算，外层限制溢出，但内部没有明确可滚动区域。

### 解决

将弹窗拆成：

```text
固定标题
固定标签页
中间内容独立滚动
固定底部操作区
```

### 验证

- 新增弹窗布局测试；
- 生产构建通过；
- 手动验证多标签、长开场白和较小窗口下可以滚动到全部字段，操作按钮始终可见。

### 预防

复杂弹窗新增字段时，必须同时检查最小窗口、长文本、键盘焦点和底部操作区。

## 案例 3：缺少模型配置可能留下空助手消息

### 现象

前端绕过配置保护或直接调用后端时，真实模型配置缺失可能在 Provider 初始化失败前已经写入用户消息和助手占位消息。

### 根本原因

模型配置校验发生在数据库写入之后，HTTP 边界、聊天编排和 Provider 初始化职责混在同一大路由文件中。

### 解决

- 前端发送前做配置预检；
- 后端 ChatOrchestrator 在写入消息前校验 Base URL、API Key 和 Model ID；
- 缺配置或不安全 URL 返回 422；
- 意外初始化失败返回 503；
- 不创建待生成消息。

### 验证

新增 5 项 ChatOrchestrator 测试，覆盖 422、503、无脏消息、错误清理和断开状态。后端总测试从 149 增至 154。

### 预防

所有有副作用的流程都应遵循“先校验、后写入”；外部服务初始化失败要映射为稳定的业务错误。

## 案例 4：前端 Store 单文件过大，AI 修改容易误删功能

### 现象

`appStore.ts` 同时处理角色、会话、聊天、设置、缓存和 UI，约 751 行。修改一个局部行为时需要理解大量无关状态，AI 辅助重构容易过度简化或遗漏。

### 根本原因

状态和动作长期追加在一个文件中，缺少明确职责边界和 Slice 级测试。

### 解决

将 Store 拆为 5 个 Slice，并提取请求保护、初始状态、聊天辅助和类型模块。组合入口降至约 26 行，同时保持原有外部 Store API 兼容。

### 验证

- 前端测试从 27 增至 30；
- 高频组件改为细粒度订阅；
- 后端 149 项回归和前端生产构建通过；
- 手动验证角色、会话、Mock 聊天、设置和运行时面板。

### 预防

大文件重构必须分阶段提交，先建立测试，再保持接口兼容，禁止用“代码变少”作为成功标准。

## 案例 5：聊天路由承担过多职责

### 现象

`api/chat.py` 约 683 行，混合 HTTP、Prompt、Provider、SSE、数据库、运行时和诊断。错误处理和资源清理难以独立验证。

### 根本原因

业务增长过程中所有聊天能力持续堆入同一个路由模块。

### 解决

提取 ChatOrchestrator，并将准备阶段、流式阶段、上下文、辅助函数和错误映射分离。路由文件降至约 82 行，公共编排入口约 97 行。

### 验证

- 原有 API 地址、请求体和 SSE 事件不变；
- 原有 149 项回归全部通过；
- 新增 5 项编排与错误测试；
- Mock、停止、重新生成、Prompt 预览和真实模型手动验收通过。

### 预防

路由只处理协议边界；跨数据库、模型和运行时的流程应由显式应用服务编排。

## 案例 6：数据库结构没有版本号

### 现象

项目依赖 `create_all()` 和手写 SQLite 补丁。当前旧库可以启动，但未来增加字段时无法确认用户数据库处于哪个结构版本，也缺少可追踪升级链。

### 根本原因

开发早期只有当前结构，没有独立迁移工具和迁移专项测试。

### 解决

引入 Alembic 1.18.5，建立 `20260717_0001` 基线；启动过程改为备份、升级、结构校验，失败恢复备份。

### 验证

- 空库建表；
- 无版本旧库接管；
- 旧字段和重复序号修复；
- 迁移幂等；
- metadata 无漂移；
- 强制失败恢复；
- 代表性 11 表数据前后哈希一致；
- 后端测试增至 159。

### 预防

任何数据库结构变化必须先创建新迁移版本，再加入“新库 + 旧库 + 失败恢复”测试。

## 案例 7：快速切换会话可能发生竞态

### 现象

会话 A 加载后立即切换到 B，A 的旧响应可能较晚返回；旧 SSE 回调也可能在新会话中继续触发。日志中还会出现同资源的并发重复请求。

### 根本原因

虽然已有基本代次保护，但缺少同资源 Promise 去重、完整缓存判定、旧流统一失效和缓存上限。

### 解决

- 按会话、资源和代次去重；
- 旧响应只写回自己的缓存；
- 会话切换或停止后旧流 token 失效；
- 最多保留 6 个最近会话缓存；
- 时间线匹配改为一次索引。

### 验证

新增 Store 竞态、缓存和流失效测试；前端测试从 30 增至 36。快速切换、生成中切换和显式停止均通过人工验收。

### 预防

异步前端不能只判断“请求成功”，还要确认响应是否仍属于当前选择、当前代次和当前流。

## 面试讲解原则

讲案例时不要说“AI 写错了，所以换一个 AI”。应说明：

1. 如何确认现象可复现；
2. 如何根据日志、请求和 Git diff 缩小范围；
3. 如何判断根本原因；
4. 修复后增加了什么自动测试；
5. 怎样避免同类问题再次发生。
