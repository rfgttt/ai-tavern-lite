# AI Tavern Lite 面试讲解指南

## 1. 60 秒项目介绍

> AI Tavern Lite 是一个本地优先的 AI 角色卡运行平台。用户可以导入 Character Card V2/V3，管理角色、世界书、开场白和 Persona，并创建单人或多人会话。前端用 React、TypeScript 和 Zustand，后端用 FastAPI、SQLAlchemy、SQLite 和 Alembic，通过 SSE 接收 OpenAI 兼容模型的流式回复。项目目前有 161 项后端测试和 36 项前端测试。我主要参与需求取舍、功能验收、Bug 复现、日志分析、自动回归、Git 版本管理，以及前端 Store、后端聊天编排和数据库迁移的工程化整理。

## 2. 用简单语言解释系统

### 前端是什么

浏览器中用户能看到和操作的部分。它负责展示角色、会话和消息，把点击和输入转换成请求，并把流式内容逐步显示出来。

### 后端是什么

服务器中的业务规则。它检查会话和模型设置，读取数据库，构建 Prompt，调用模型，保存最终消息和运行时状态。

### 数据库是什么

保存角色、会话、消息、设置和状态的长期存储。项目使用 SQLite，因为它适合本地单用户工具，不需要单独安装数据库服务。

### HTTP 是什么

前端和后端交换请求与响应的协议。GET 常用于读取，POST 用于创建或执行操作，PUT 用于更新。200 表示请求成功，4xx 通常是请求或配置问题，5xx 通常是服务器未处理的问题。

### SSE 是什么

服务器通过一个持续的 HTTP 连接不断向浏览器发送事件。它适合模型逐字生成，因为当前只需要服务器单向推送，不需要 WebSocket 的全双工复杂度。

## 3. 你的贡献怎么说

建议使用：

> 项目采用 AI 辅助开发。我不是把所有代码都说成完全独立手写，而是持续负责需求拆分、功能验收、问题复现、日志判断、测试执行、Git 提交和回归验证。随着项目推进，我也开始理解和参与 Store 分层、ChatOrchestrator、SSE 状态、Alembic 迁移和请求竞态等具体实现。

不要使用：

> 整个系统都是我一个人从零手写的。

也不要使用：

> 我什么都不懂，代码全是 AI 写的。

更准确的定位是：

> 我使用 AI 提高实现速度，但通过测试、日志、差异检查和手动验收控制交付质量。

## 4. 常见追问

### 为什么做这个项目

角色卡聊天涉及界面、模型 API、数据库、流式通信和状态管理，适合练习完整产品交付。早期项目因大文件耦合和缺少测试重构失败，因此新项目重点加入版本控制、测试和模块化。

### 为什么选择 SSE 而不是 WebSocket

核心需求是模型单向持续输出。SSE 建立在 HTTP 上，协议和浏览器处理更简单，也方便通过反向代理。当前没有实时多人协作，因此不需要 WebSocket。

### 为什么需要 Mock 模式

它让安装、测试和演示不依赖外部网络、余额和 API Key。出现问题时也能先判断是本地业务逻辑还是模型供应商。

### 如何防止 AI 把代码改坏

- 修改前确保 Git 工作区干净；
- 大改动先建立自动测试；
- 补丁应用前做 SHA-256 校验和备份；
- 查看 `git diff`，警惕小需求删除大量代码；
- 运行后端、前端、构建和手动主流程；
- 每个稳定阶段单独 commit。

### 最有价值的 Bug 是什么

优先讲 SSE `[DONE]`、配置错误留下脏消息、快速切换会话竞态或 Alembic 旧库接管。使用“现象—复现—原因—修复—验证—预防”结构。

### Alembic 解决了什么

它给数据库结构增加版本链。空库可以按迁移创建，旧无版本数据库可以接管，未来增加字段可以按版本升级。迁移前备份，升级后校验，失败时恢复。

### 1002 条消息测试说明了什么

说明后端接口可以完整、有序返回长历史，消息序号连续；时间线匹配也从逐条查找优化为索引读取。但它不等于浏览器已经支持无限消息，虚拟列表仍是后续性能工作。

### 项目有哪些不足

- 当前是本地单用户；
- SQLite 和活动流状态不适合多实例；
- 未完成公网部署验收；
- 超长消息列表未虚拟化；
- 自己的基础代码能力仍在补充，需要继续提高独立修改和解释能力。

主动说清限制，比把项目说成“已经完全生产化”更可信。

## 5. 测试岗位重点表达

- 能写正常、异常、边界和安全场景；
- 能从日志定位 HTTP、SSE、数据库或前端状态问题；
- 能区分人工验收和自动回归；
- 能把历史 Bug 变成测试；
- 能执行发布门禁并判断是否允许提交；
- 能说明数据迁移为什么需要备份和恢复测试。

## 6. 产品助理重点表达

- 能发现长弹窗不可操作、错误提示不明确等体验问题；
- 能把新会话拆成角色、Persona、编组、开场和初始状态选项；
- 能定义配置缺失时的用户提示和后端行为；
- 能区分必须完成、可以延后和不应无限扩张的功能；
- 能用测试结果和日志作为验收依据。

## 7. 现场可能要求的操作

至少练习以下任务：

1. 用自己的话画出发送消息的完整链路；
2. 找到一个后端 API 路由及其 Service；
3. 使用 `git status` 和 `git diff` 检查修改；
4. 运行一个指定 pytest 或 Vitest 文件；
5. 根据一个 400/422/500 日志说明排查顺序；
6. 写一条角色创建接口的测试用例；
7. 使用 SQL 查询某个会话的消息数量；
8. 解释为什么迁移失败后不能只看“应用还能启动”。

## 8. 面试前自测标准

能够不看稿回答：

- 项目解决什么问题；
- 前端、后端和数据库各自负责什么；
- HTTP 和 SSE 的区别；
- 一次消息如何被保存；
- 如何停止流式生成；
- Alembic 的作用；
- 3 个真实 Bug；
- AI 在项目中的作用和边界；
- 当前限制和下一步计划。
